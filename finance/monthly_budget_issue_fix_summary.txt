Ledger column K — issue #2 fix
Date: 2026-09-04
Live file: /home/himanshu/Documents/Finance/Finance-Mng-V2.xlsx

Verdict
-------
Real, and worth fixing. Not a dashboard-rebuild item.

The phone/API path was already safe: finance/sync.py writes K as =TRUE() or
=FALSE() on every append. The silent failure is LibreOffice / typed-in rows
on the prefilled empty zone.

What I found on inspection
--------------------------
- Last transaction: row 157 (03-Sep-2026). K157 = TRUE(). All 156 dated rows
  already have K as =TRUE() (134) or =FALSE() (22).
- Rows 158–197: Day/Month/Year formulas present; K blank. Yellow input fill
  already there, plus a TRUE/FALSE dropdown on K2:K988.
- Row 198+: even C/D/E stopped. A typed row there would also miss Month/Year,
  so Monthly Budget SUMIFS would ignore it too.
- No Excel Table on Ledger.
- SUMIFS on Monthly Budget use Ledger!$K:$K,TRUE() / FALSE(). A blank K does
  not match TRUE(), so the transaction is dropped from Budget Expenses.

Why not an Excel Table
----------------------
Issue #1 already showed LibreOffice rewriting structured refs back to a frozen
A1 range. K is also an override column (mixed =TRUE()/=FALSE() on real rows,
including Expense rows that are intentionally FALSE: flights, medical, laptop,
education). A table calculated column would fight those overrides. Prefill
through the same expandable range is the practical fix.

What changed (surgical — no dashboard rebuild)
----------------------------------------------
Sheet: Ledger only
- Existing rows 2–157: untouched (content hash unchanged).
- Empty rows 158–2000: C/D/E formulas kept/extended; K now
    =IF(A{row}="","",IF(OR(F{row}="Expense",F{row}="Refund"),TRUE(),FALSE()))
  Blank until Date is set. Expense/Refund default TRUE; Income, Transfer,
  Credit Card Payment, Investment, Adjustment default FALSE. Override via the
  dropdown (or type =FALSE() / =TRUE()) still works — same as today.
- Autofilter and list validations widened to row 2000.
- Category-level Typical Budget? is not auto-wired (Rent/EMI/Medical still
  need a manual K override when they should be out of budget). That is a
  default, not a second source of truth.

Not changed
- Simple Dashboard, Detailed Dashboard, Monthly Budget, Reconciliation,
  Planned Expenses, Configuration.
- No Ledger data values, types, amounts, or existing K flags.

Code (so a future blank build / phone append cannot recreate the gap)
- finance/build_workbook.py: template prefills C/D/E/K through row 2000;
  surgical flag --ledger-prefill.
- finance/sync.py: after append/update/delete, keep ≥80 formula rows below
  the last transaction (and at least through row 2000).
- finance/import_statements.py: extra empty rows also get the K default.

Free to allocate — issue #3 fix
Date: 2026-09-04
Live file: /home/himanshu/Documents/Finance/Finance-Mng-V2.xlsx

Verdict
-------
Real, and worth fixing. Not a dashboard-rebuild item.

The old number (liquid − budget remaining) is leftover after the
discretionary cap, not cash you can move to FD / invest / goals. After
payday it looked allocatable while CC due, remaining SmartEMI, and
near-term one-time plans were still claims on the same savings.

What I found on inspection
--------------------------
Live (4 Sep 2026), not the reviewer's stale remaining-budget figure:

  Liquid savings                 ₹25,031.25
  Budget remaining               ₹4,598.96   (₹31,000 − ₹26,401.04 spent)
  Old free to allocate           ₹20,432.29
  CC due                         ₹1,030.20
  Planned recurring this month   ₹63,327     (Loan/EMI ₹38,200 + Lifestyle ₹25,127)
  Planned one-time (30d)         ₹7,500      (HYD to DEH, Status=Planned)

Rent ₹10,800 (2 Sep) and Family Payment ₹10,000 (1 Sep) are already paid
from HDFC Savings with Include in Budget = TRUE. They already reduced
liquid and budget remaining. Subtracting the full Planned Expenses month
total (₹63,327) on top of budget remaining would double-count them and
the other budgeted lifestyle rows (electricity, internet, subs).

MacBook SmartEMI ₹38,200 is billed to HDFC CC (first due 12 Sep), not yet
in this month's Ledger. Category EMIs / Typical Budget? FALSE — it is
outside the ₹31k cap. The ₹20k FD on 2 Sep is exactly the kind of move
the old metric would have called "free".

Practical definition (avoids double-counting)
---------------------------------------------
  Budget remaining  = unused discretionary cap this month
  Committed cash    = CC due
                    + MAX(0, this-month planned Loan/EMI − Ledger EMIs this month)
                    + Planned one-time next 30 days (Status=Planned)
  Free to allocate  = liquid − budget remaining − committed cash

When the EMI posts to the card, remaining EMI falls to 0 and CC due
picks it up — committed stays the same, no double-count.

Not subtracted (would lie the other way):
  - Full Planned Expenses P6 / Lifestyle N6 (overlaps the budget cap)
  - Remaining rent/family (inside Include in Budget on this workbook)
  - Planned investments (that is what free cash is for)

What changed (surgical — no dashboard rebuild)
----------------------------------------------
Sheet: Simple Dashboard
- A14 title: after budget, bills, near-term plans
- A17/B17 Committed cash (was the old Free line)
- A18/B18 Free to allocate = liquid − budget reserved − committed
          (used the previously blank row 18; Planned Expenses block unmoved)
- Next-month line "− Pay all CC dues" → "− Next month Loan / EMI"
  (CC is already inside today's free; do not subtract it twice)
- Est. free next month formula unchanged in shape:
    free today − next EMI + salary − next budget

Sheet: Detailed Dashboard
- B22 Free to allocate uses the same subtractions (liquid − budget − CC
  − remaining EMI − 30d one-time). No extra rows (layout is tight).
- E24 same next-month EMI swap; E27 still E23−E24+E25−E26
- Note at A23 updated

Not changed

Planned Expenses formulas — issue #5 fix
Date: 2026-09-04
Live file: /home/himanshu/Documents/Finance/Finance-Mng-V2.xlsx

Verdict
-------
Real as a maintainability problem, and practical to fix. Not a dashboard
rebuild. The reported #VALUE! is not what LibreOffice Calc currently does.

What I found on inspection
--------------------------
NEXT 6 MONTHS (L6:P11) was 18 SUMPRODUCT formulas, ~670–730 characters each.
Each one mixed:

  Active TRUE() vs "TRUE", Kind (or blank → infer from Category),
  Monthly vs Yearly, Start/End overlap, and MONTH()/DATE() on Start.

The yearly half calls MONTH($E$15:$E$64) across the whole block. Rows 28–64
are empty, so that is MONTH() on blanks inside an array. Calc coerces those
and the sheet currently calculates. A renderer that does not coerce them
gets #VALUE! on Monthly Fixed Cost (B5=P6) and the Loan/Lifestyle/Investment
forecast — which is what the review saw. Issue #3 already wrapped M6 in
IFERROR for that reason.

LibreOffice on a copy of the live book, before this change:

  Sep 2026  Loan ₹38,200  Lifestyle ₹25,127  Total ₹63,327
  Oct 2026  Loan ₹38,200  Lifestyle ₹11,127  Total ₹49,327
  Dec 2026  Loan ₹38,200  Lifestyle ₹12,927  Total ₹51,127
            (Dec includes himanshu-gupta.com ₹1,800)
  6-month   Loan ₹2,29,200  Lifestyle ₹82,562  Total ₹3,11,762

Those numbers match the Python due-in-month logic. So Calc was right;
the formulas were still unauditable and a latent bomb in other engines.

Practical design
----------------
Do not keep the date/Kind logic inside the aggregate. Put it on the row,
then SUMIFS.

Dashboard anchors stay L6:P12 / B5=P6 (Simple + Detailed + committed cash
already point here). Helpers sit to the right so they cannot collide with
that table.

  Q  Active?          TRUE/FALSE from G (boolean or "TRUE" text)
  R  Effective Kind   Kind, or EMIs → Loan / EMI / Investment → Investment
                      / else Lifestyle
  S–X  cash due       one column per forecast month L6..L11

Cash-due is nested IF, so MONTH() only runs when Start is non-blank.
Empty Start = already started; empty End = no end. Inactive → 0.

Skipped separate "Monthly Due?" / "Yearly Due This Month?" booleans: they
would have to be copied for each of the six months. S–X is Effective
Monthly Cash for those months.

Forecast:

  M6 = SUMIFS($S$15:$S$64,$R$15:$R$64,M$5)   (Loan / EMI this month)
  N6 = SUMIFS(..., N$5)                     (Lifestyle)
  O6 = SUMIFS(..., O$5)                     (Investment)
  M7 uses column T, M8 uses U, … M11 uses X.

What changed (surgical — no dashboard rebuild)
----------------------------------------------
Sheet: Planned Expenses only
- Recurring rows 15–64 columns A–K: untouched (content hash unchanged).
- One-time rows 66–97: untouched.
- Added Q13:X64 helper header + formulas (green). Q65 note.
- Rewrote M6:O11 from SUMPRODUCT to SUMIFS on R + S–X.
- L6:L11, P6:P12, B5=P6 unchanged in role.
- A11 note mentions the helpers.

Not changed
- Ledger, Monthly Budget, Reconciliation, Configuration.
- Simple / Detailed dashboard layout and formulas (they still read M6:P12
  and B5:B10). Remaining EMI still prefers M6, now a SUMIFS.
- Recurring amounts, dates, Active, Kind, Payment Method, Notes.
